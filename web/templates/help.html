Llama Toolchest — Help

A product manual for running local LLMs with the llama.cpp inference server, wrapped in a web UI.

Quickstart

  1. Build llama.cpp. Go to Builds, pick a profile that matches your hardware (CUDA, ROCm, Vulkan, CPU), and start a build. Builds are cached and reused.
  2. Download a model. On Search HF, search for a GGUF repo (e.g. unsloth/Qwen3.5-4B-GGUF) and download a quant (Q4_K_M is a good balance for most).
  3. Enable it. On Models, flip the "On" switch for the model(s) you want the server to serve.
  4. Tune for VRAM. Click Configure on a model to adjust what matters most: Context Size (smaller = less KV cache = less VRAM) and KV Cache Quant (q8_0 roughly halves KV memory with little quality cost). Watch the VRAM Est. column update so you can see the model fit.
  5. Start the server. Go to Server and click Start. Use the icon in the Available Models card to force-load a model into VRAM, or let the router load it on the first request.
  6. Send a request. Use the OpenAI-compatible endpoint listed in the API Endpoint card, passing a model's public name (e.g. unsloth-Qwen3.5-4B.Q4_K_M) in the model field.

Core concepts

Enabled vs loaded

These are two different things:

Enabled
The model is included in the llama.cpp preset file and advertised via /v1/models. The router knows it exists and can load it on demand. You can enable as many models as you like. Enabling does not use any VRAM.
Loaded
The model's weights are actually resident in GPU VRAM and ready to serve a request. Only a limited number can be loaded at once (Max Loaded on the Server card). The router loads a model when the first request arrives or when you click the icon in the Server tab's Available Models card.

So: "enabled" means "available to serve"; "loaded" means "actively in VRAM now".

Max Loaded

Caps how many models can be simultaneously resident. When the cap is hit and a request comes in for another enabled model, the router unloads the least-recently-used one to make room. Set to 0 for unlimited (not recommended unless you really do have the VRAM).

Public model names

The id returned by /v1/models is a short name derived from the HuggingFace repo and quant — e.g. unsloth-Qwen3-Coder-Next.UD_Q8_K_XL. The long registry ID still works as an alias. Use the copy icon in the Server tab to grab the name for your client.

Presets & aliases

Each enabled model's flags and aliases are handed to llama-server when it starts. User-defined aliases (set in Configure → Aliases) are added alongside the auto-generated ones, so you can refer to a model by any of: public name, registry ID, or your own alias.

Server tab

The single page you'll spend the most time on. It combines live status, server controls, and logs.

Server card

  • State badge — Stopped / Starting / Running / Failed.
  • Build — which compiled llama.cpp to run. Auto (newest ref) picks the successful build with the highest bN tag.
  • Max Loaded — see above.
  • Start / Stop / Restart — control the llama-server process.

Available Models card

Lists every enabled chat model by public name. Each row has:

  • A load icon — force-loads the model into VRAM. Only appears when the model is not yet loaded.
  • A copy icon — copies the public name to the clipboard.
  • A loaded / loading tag when the router has it resident.

Inventory & API Endpoint cards

Build/model counts and the OpenAI-compatible base URL for your clients.

Live Performance

Passive timing summary collected from every /v1/chat/completions request that flows through the proxy — no explicit benchmark needed. Shows rolling averages of generation and prompt-processing speed per model, so you can see real-world performance as you use the server. Both streaming and non-streaming requests are captured.

Server Logs

Live-tailing stdout/stderr from llama-server. Live tail auto-scrolls. Copy dumps to clipboard; Clear wipes the pane (does not clear backend history).

Builds

llama.cpp must be compiled against your hardware. The Builds tab checks out a ref from ggml-org/llama.cpp, configures cmake for a backend profile, builds, and keeps the resulting llama-server binary. Multiple builds can coexist — you pick the active one on the Server tab.

Profiles

The Profile dropdown only lists backends detected on this system — the SDK or driver for a backend must be present for it to appear (no CUDA toolkit → no CUDA option, and so on).

CUDA
NVIDIA GPUs. Requires the CUDA toolkit.
ROCm
AMD GPUs. Requires ROCm. The GPU arch is auto-detected from rocminfo when possible (e.g. gfx1201 for Radeon R9700), falling back to gfx1100 if detection fails. To target a different arch, set GPU_TARGETS in the Extra CMake Flags box.
Vulkan
Vendor-neutral GPU acceleration (AMD, NVIDIA, Intel) through the Vulkan driver — handy when you don't have a vendor SDK installed. Host-mode only: Vulkan isn't offered when running inside a container, since that requires host driver/ICD passthrough the container doesn't manage.
Metal
Apple GPUs. Only appears when running on macOS.
CPU
Portable build with no GPU acceleration. Always available.

Ref selection

Choose a specific llama.cpp release tag (b*) or latest to auto-pick the newest. Some features (like experimental tensor parallelism) only exist after a certain ref — and a few go the other way: rocWMMA FlashAttention was removed upstream at b10332, so its toggle only affects refs older than that. It remains the fastest prompt-processing path on RDNA4 (the replacement kernel is 25–49% slower at deep context on gfx1201, upstream issue #26220), so RDNA4 users chasing prompt speed should pin an older ref and enable it.

Build options

The toggles under each profile are a curated set: every one offers a real performance or compatibility payoff on refs you'd build today, with the description saying when to enable it. Debug-only flags (like the Vulkan validation layers) and flags removed upstream aren't offered as toggles — anything else llama.cpp's CMake accepts can go in the Extra CMake Flags box, and the effective-flags preview shows exactly what the build will receive either way. Vulkan has no performance build flags at all upstream; its tuning levers are runtime environment variables under Settings.

Saved flag sets

A favorite combination of toggles and Extra CMake Flags can be saved and replayed against any git ref: set the flags, enter a Build Tag (it names the set), and press Save Flags. Picking a set from the Saved Flag Sets dropdown fills the toggles, extra flags, and Build Tag — so builds made from it are labeled by the flag set that produced them (e.g. b10440-rocm-rocwmma). Saving under an existing name updates it; sets belong to a profile and store no git ref.

Models

Every downloaded GGUF shows up here. The list is grouped by HuggingFace org, then by base model name (the repo minus -GGUF), with all quants of a base model shown together.

Controls

Filter box
Substring match across org, base name, quant, public name, and architecture. Matching rows auto-expand their group.
Collapse / Expand All
Toggle every org group at once. Per-base-model collapse state is preserved across org toggles.
On switch
Enable/disable the model. Disabled models are not served; restart the server to fully remove from its registry.
Configure
Expands an inline form to edit per-model flags (see below).
Remove
Removes the model from the UI. Choose "Keep Files" to leave GGUFs on disk, or "Delete Files" to also remove them.

VRAM Est. column

Shows base (weights + small overhead) and peak (weights + full KV cache at configured context size). The GPU allocation map uses the peak number so the bars reflect actual VRAM use when a model is loaded.

Downloads card

A single Downloads card at the top of the Models page tracks every download — one row per model, whether it's actively downloading, paused, or was interrupted. Active rows show live progress and a Pause button (stops the transfer but keeps the partial files); paused or interrupted rows show what's on disk with Resume (picks up from the bytes already downloaded) and Discard (deletes the partial files). Rows persist across restarts — an interrupted download reappears as paused on the next boot — and leave the card only when the download completes or you discard it. To fully cancel a download: Pause, then Discard.

Incomplete & missing files

If a registered model's download was interrupted, its card carries an incomplete badge and a Resume button; it can't be enabled until the download finishes. If a model's GGUF has gone missing from disk entirely, it's flagged as an orphan and likewise can't be enabled — remove it or re-download.

Model config (Configure dialog)

GPU Assignment

A single dropdown that chooses how the model is spread across your GPUs:

GPU N
Pin to a single GPU.
GPUs i-j
Contiguous range, layer split — each GPU holds a sequential slice of layers.
All GPUs (layer split)
Layer split across every GPU.
Tensor Parallelism (N GPUs)
Experimental. Splits individual tensors across N GPUs simultaneously — needs a fast GPU interconnect. On CUDA, NCCL (libnccl-dev) must be present at build time for the optimized AllReduce path; without it the build falls back to a slower path. Pair with Flash Attention on and KV cache at f16 (no quant). Upstream support is still rough for some architectures, and N must divide the model's attention head count — many models pick head counts that don't split by 3.
Custom
You provide a raw --tensor-split ratio string.

Any option that leaves GPUs out is enforced with a --device list, so the excluded GPUs are never even initialized by that model's server instance — they stay idle and free for other models. (A zero tensor-split entry alone only keeps weights off a GPU; llama.cpp would still initialize it and, in tensor mode, spin it at 100% inside the collective ops.) The Custom option skips this and passes your ratio string through untouched.

Integrated GPUs. On a box with both a discrete card and an APU, options touching the iGPU are labeled (iGPU) and never auto-recommended, and the spanning options — All discrete GPUs and Tensor Parallelism — cover the discrete cards only. The iGPU stays selectable for those who built with the Include iGPU Build Target toggle; picking it under the default build (which compiles no kernels for it) shows a warning, since the model would fail to load. APU-only machines are exempt — there the iGPU is simply the GPU.

Key flags

GPU Layers
How many layers to offload. 999 means "all"; lower values keep some on CPU.
Context Size
Token context window. Larger = more VRAM for the KV cache. "Model Default" uses the training context length.
Flash Attention
Usually safe on, faster and lower VRAM.
Jinja Templates
Required for most modern chat models to render their prompt format.
KV Cache Quant
Quantize the KV cache. q8_0 is a ~50% VRAM win with almost no quality cost; q4_0 saves more but can affect quality.
Direct I/O
Load model weights straight to VRAM, bypassing the OS page cache. Useful when VRAM > system RAM.
Micro-batch (-ub)
The physical batch actually computed at once, and usually the biggest lever on prompt-processing speed. Larger values generally raise prefill throughput at the cost of compute-buffer VRAM, but the optimum depends on both the model and the GPU — measure it with a benchmark sweep rather than guessing. Must be ≤ Batch. Blank leaves llama.cpp's default of 512.
Batch (-b)
The logical batch: tokens submitted per decode call, processed in micro-batch-sized chunks. Mostly just needs to be ≥ Micro-batch. Blank leaves llama.cpp's default of 2048.
Vision Projector (mmproj)
Multimodal projector path. Auto-detected from the model directory for most vision models.

Speculative Decoding

Predict multiple tokens per step for a speedup with no quality change. Draft Model uses a smaller same-architecture model as the drafter (largest and most consistent speedup). N-gram modes use pattern matching with no extra model — best for repetitive workloads. Click the ? button in the Configure dialog for per-mode details.

Sampling

Temperature, top-p, top-k, min-p, penalties — applied per-request with no restart needed. Leave blank to use server defaults. When a model is downloaded (or found by a scan), recommended presets are gathered automatically from three sources, in order: sampling defaults embedded in the GGUF file itself (general.sampling.* metadata, shipped by all major quantizers since late 2025), the Unsloth docs page for the model family (which adds thinking / non-thinking / coding variants and parameters vendors omit), and the base model's generation_config.json on HuggingFace. The Preset dropdown offers whatever was found, each labeled with its source — pick one to fill in the fields, then tweak as you like.

One subtlety: for recent GGUFs, blank fields do not mean "no sampling opinion". llama-server reads the file's embedded defaults on its own and applies them whenever nothing overrides them, and the config form notes when that's the case. Picking a preset or typing a value takes precedence.

The ↻ Refresh presets button re-runs the lookup — useful when you grabbed a model on release day, before its docs page existed.

Extra Flags

Free-form llama-server flags appended verbatim. Use for anything not exposed in the UI.

Most config changes require a server restart to take effect (the flags are baked into the preset file that llama-server reads at startup). Sampling params apply per-request with no restart.

Search HF

Search HuggingFace for GGUF repos, browse files, and download specific quants. Downloads resume on interruption. Large models are shown with their total size so you know what you're committing to. After a download completes, recommended sampling presets are fetched automatically in the background and appear in Configure → Sampling.

Gated models require a HuggingFace token — set it under Settings.

Vision models & projector files

Some vision-capable LLMs ship as two files: the main GGUF (text+vision weights) and a separate mmproj file (the vision projector — maps image embeddings into the model's text space). On HuggingFace these usually live in the same repo, with names like mmproj-model.gguf.

  • Downloading the main GGUF does not automatically fetch the mmproj. You need to click it in the file list to download it too.
  • Once the mmproj is downloaded into the same model directory, it's auto-associated with its LLM — the Configure dialog's Vision Projector (mmproj) field fills in automatically.
  • If the LLM has vision baked in (no separate projector needed), the Configure dialog shows Vision: Built-in and there's nothing to download.
  • mmproj files show up in the file list with a small badge but are not registered as standalone models.

If an mmproj ends up in an unexpected location, you can paste its path into the Configure dialog's Vision Projector field manually.

Benchmarks

Benchmarks are organised as jobs: a named batch that runs a matrix of models × builds × presets, optionally multiplied by a sweep over any model parameter. Every cell records the build (including its CMake flags), the config in effect, and the GPU state, so a result stays interpretable after you rebuild or delete things.

Measurements run as real end-to-end requests through the router, or via llama-benchy for the benchy-* presets. Both work with multi-file (sharded) GGUFs.

Presets

internal-quick (~10s)
One request, 256-token prompt, 128 generated. Sanity check that a model loads and responds.
internal-standard (~1 min)
Three repetitions at 128 / 512 / 2048-token prompts, 128 generated each.
internal-thorough (~5 min)
Five repetitions at 128 / 512 / 2048 / 8192-token prompts, 256 generated each. Tight variance bounds.
internal-long-ctx
A single 32K-token prompt with 512 generated. Stresses KV cache and flash attention.
internal-long-ctx-thorough (~20 min)
Three repetitions at 8K / 16K / 32K / 64K-token prompts, 512 generated each. Use this when comparing builds at long context, where one repetition is too noisy to tell a real difference from run-to-run variance.
benchy-quick / benchy-standard
Run through llama-benchy against the router's OpenAI-compatible endpoint.

Prompt sizes are nominal. Prompts are built at an estimated 4 characters per token, so the tokenized length usually comes out 10–25% lower depending on the tokenizer — check prompt_tokens in the results for what was actually sent.

Parameters and sweeps

Each parameter in a job defaults to every model's own saved setting. Pick one value to use it for the whole job; pick several and each becomes its own cell. There is no separate "override" concept — one value is an override, more than one is a sweep.

Parameters marked ↻ reload llama-server for each distinct value, which is what makes a sweep slow. Sampling settings ride along with each request and cost nothing extra. The matrix preview shows both the cell count and the estimated number of reloads before you commit.

A job's parameters are applied to a throwaway preset file; your saved model configs are never modified, so a cancelled or crashed job cannot leave a model misconfigured.

Finding a good micro-batch: -ub is usually the biggest lever on prompt-processing speed, and the best value depends on both the model and the card — there is no default worth trusting. Select a model, a build and a long-context preset, then pick several micro-batch values (or use Find best micro-batch) and compare the PP column.

What gets measured

  • PP t/s — prompt processing speed: how fast the model ingests your input. This is what determines "time waiting before streaming starts".
  • TG t/s — token generation speed: the streaming rate users actually feel.
  • TTFT — time to first token, including prompt processing. Lower = snappier perceived response.

Actions

  • Detail — expands the job's cell matrix, with each cell's sweep point and per-run data.
  • Compare — check multiple rows and hit Compare to see them side by side, within or across jobs.
  • Export — CSV or JSON, including the build's CMake flags and each run's sweep point so rows stay distinguishable outside the UI.
  • Retry failed — re-runs only the cells that failed, keeping completed results.
Runs marked ⚠ unverified: these predate the fix that made job parameter overrides take effect. Their throughput numbers are real, but the config recorded against them may not be what actually ran. Re-run them if the configuration matters to your comparison.

A failed benchmark still appears in the list and can be deleted like any other.

Settings

Auto-start
Start the llama-server automatically on startup (container boot or service start), using the selected build and model configs.
Runtime environment
Environment variables applied to the llama-server router process and inherited identically by every model instance it spawns — process-wide, not per model — taking effect on the next restart. A backend dropdown filters the table view (defaulting to the active build's backend, but any backend's variables can be set at any time — with or without a build for it); a variable with a value set stays visible in every view, so nothing applies invisibly. The curated list is deliberately short: most environment variables that circulate as llama.cpp tuning tips are either no-ops for it or workarounds for other stacks — leave them unset unless you are measuring a specific difference. The Extra environment box takes anything else, one KEY=VALUE per line; it's applied last, so it overrides the dropdowns on a name clash, and known-footgun variables (device-visibility overrides, HSA_OVERRIDE_GFX_VERSION, CUDA_DEVICE_ORDER) save with a warning explaining the hazard. The Effective environment preview shows the final list as the launch will apply it — a value already exported around the service (a systemd drop-in, container env) wins over one set here, and the preview marks those.
Backup & Restore
Exports configuration intent as a single versioned JSON file: preference settings, runtime environment, saved build flag sets, and per-model launch configs keyed by HuggingFace identity (org/repo + quant) rather than file paths — so a backup restores onto a different server. Secrets (HF token, API key) are included only via an explicit checkbox, in plaintext. Restore is selective (per-section checkboxes with a client-side file preview that flags secret-bearing files) and a merge: it never deletes anything, GPU assignments are re-resolved for the local hardware with warnings for anything that couldn't map, and configs for models not installed become pending — shown as greyed cards on the Models page with Download/Discard actions, attaching automatically when the matching model arrives (even weeks later, from any download or scan). Deployment-identity settings (listen address, ports, paths, active build) are recorded in the file for reference but never applied. Scripting: GET /api/backup (add ?secrets=1) and POST /api/restore (multipart file + sec_settings/sec_env/sec_flags/sec_models) — same-origin routes, protected only by your deployment's network posture like the rest of /api. Benchmark history is not included; use the benchmark export for that.
Server URL
The externally-reachable base URL of this web UI — used for the clickable API endpoint and Chat UI links. Change this if you access the UI from another host.
OpenAI-Compatible Proxy
The /v1 endpoint exposed to clients. Test Connection verifies the llama-server is reachable.
API Key
Optional Bearer token required for /v1/* requests. Leave blank for an open proxy.
HF Token
Required to download gated models.
Theme
UI color scheme (Dark, Light, Terminal Green, Terminal Amber, Cyberpunk). Saved per-browser in localStorage.
Data directory
Where builds, registry state, and (by default) models live. Shown for reference — it's set at install time in the config YAML, not editable here.
Models directory
Optional override for where GGUF files live and where new downloads land. Blank uses <data dir>/models. Must be an absolute path to an existing directory; restart the service after changing it.

Using the API

The server speaks the OpenAI /v1/* dialect. Point any OpenAI-compatible client at the proxy endpoint.

curl $BASE/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "unsloth-Qwen3.5-4B.Q4_K_M",
    "messages": [{"role": "user", "content": "hello"}]
  }'

Pass any of these in the model field: public name, registry ID, auto-discovery name, or a user-defined alias. The router loads the model on first request (may take a few seconds).

Troubleshooting

Start button does nothing
No successful build exists. Go to Builds and build llama.cpp first.
"no compiled build available"
Same — the selected build failed or none exist.
Model won't load / crashes llama-server
Check the Server Logs. Tensor parallelism is experimental and may fail on some architectures. Try switching GPU Assignment to a layer-split option.
Model doesn't appear in /v1/models
Verify the "On" switch is flipped, then restart the server so the preset file regenerates.
Model still shows as "loading" forever
It likely failed at startup — check Server Logs for the error.
Out of VRAM
Lower GPU Layers, reduce Context Size, enable KV Cache Quant, or lower Max Loaded. The GPU allocation map on the Models page shows where your VRAM is going.
No sampling presets for my model
The lookup found nothing: an older quant without embedded defaults, no Unsloth docs page for the family, and no usable generation_config.json. The fields fall back to server (or GGUF-embedded) defaults. Use ↻ Refresh presets in Configure → Sampling to retry after the publisher adds documentation.
