Llama Toolchest — Help

Run local LLMs with llama.cpp, plus image, video and music generation, from one web UI.

Quickstart

  1. Build llama.cpp. On Builds, pick the profile for your hardware (CUDA, ROCm, Vulkan, CPU) and start a build.
  2. Download a model. On Download Models, Find recommended LLMs lists models that fit this machine, or search for a GGUF repo and pick a quant (Q4_K_M is a good default).
  3. Enable it. On Models, turn on the model's On switch.
  4. Autoconfigure it. Press Autoconfigure on the model, say how long your conversations or documents are, review the proposed settings and press Save and apply. It works out what fits in your GPU memory and test-loads it. For the publisher's advice too, install the helper model on Settings first.
  5. Start the server. On Server, press Start.
  6. Autotune it (optional). Press Autotune on the model to measure faster speed settings, then Use these settings on the result you want. It takes a while, and the server cannot answer other requests while it runs.
  7. Send a request to the OpenAI-compatible address in the API Endpoint card, with the model's public name in the model field.

Core concepts

Enabled
The server offers the model in /v1/models and can load it on request. Uses no GPU memory. Enable as many as you like.
Loaded
The model is in GPU memory and ready. The router loads it on the first request, or when you press in the Server tab's Available Models card.
Max Loaded
How many models can be loaded at once. When it is reached, the least recently used one is unloaded. 0 means no limit.
Let the router keep several models loaded
Lets the llama-server router decide by GPU memory instead of by count: it keeps models loaded, for example small embedding or speech models beside a large chat model, and when a new one does not fit it unloads the least recently used idle ones until it does, keeping a margin free on each GPU (shown under the switch). A model answering a request is never unloaded. A small model can unload a big one: if a big chat model leaves less room on a GPU than a small embedding model needs (plus the margin), a request for the embedding model unloads the chat model. To keep both loaded, give the big model a smaller context so it leaves that room. It needs llama.cpp b11930 or newer, and it is only available while generation backends are off: the router cannot see their GPU reservations, so toolchest's own unloading decides while they are on. Benchmarks and Autotune still load one model at a time.
Public name and aliases
The id in /v1/models is a short name from the repo and quant (e.g. unsloth-Qwen3.5-4B.Q4_K_M). The long registry ID and any aliases you add in Configure → Aliases work too.

Builds

Builds compile llama-server from a ggml-org/llama.cpp ref for one backend. Several builds can be kept; choose one on the Server tab.

Profiles
Only backends found on this system are listed. CUDA: NVIDIA, needs the CUDA toolkit. ROCm: AMD; the GPU arch is detected (set GPU_TARGETS in Extra CMake Flags to change it), and with more than one ROCm installed a ROCm Install picker appears. Vulkan: any vendor, host installs only. Metal: macOS. CPU: always available.
Ref
A release tag (b*) or latest. rocWMMA FlashAttention was removed at b10332 but is still the fastest prompt reading on RDNA4; pin an older ref to use it.
Options and Extra CMake Flags
Each toggle says when to use it. Anything else CMake accepts goes in Extra CMake Flags; the preview shows the final flags. Vulkan tuning is runtime environment variables in Settings.
Saved flag sets
Enter a Build Tag and press Save Flags to keep toggles and extra flags under that name, then replay them on any ref.

Autoconfigure and Autotune

A profile is a named copy of a model's settings. The profile bar at the top of Configure saves and restores them. Profiles survive re-downloading the model and are included in backups.

AutoconfigureAutotune
DoesSuggests settings that fitMeasures many settings and keeps the fastest
SetsContext size, KV cache type, GPU layers, expert offload, GPU placement, samplingBatch sizes, flash attention, split mode, threads, speculative decoding
AsksHow long your conversations or documents areWhat you use the model for (speculative decoding pays off most when answers repeat the prompt, as in code editing)
ResultA reviewed list of settings, each with a reason; Save as profile or Save and applyUp to three profiles: fastest generation, fastest prompt reading, fastest full answer
While it runsTest-loads the settings (restarts the server, unloads other models)Restarts the server for each setting; stop any time and continue later
  • Run Autoconfigure first. Autotune keeps context, memory and sampling settings as they are, so it makes a badly set-up model faster but not right.
  • Test load. The memory estimate adds all GPUs together, but llama.cpp does not fill them evenly. If the test load runs out of memory, Autoconfigure tries, in order: fewer layers on the full GPU, a smaller prompt batch, a smaller context. Those settings are marked test load.
  • Helper model. Autoconfigure reads the model card with a small model of its own (install it on Settings). Without it, settings come only from what fits.
  • Noise. Autotune keeps the simpler setting unless the faster one wins by more than the run-to-run variation. Each stage is an ordinary benchmark job you can read on Benchmarks.

Model config (Configure)

GPU Assignment

GPU N / GPUs i-j / All GPUs
One GPU, or layers split across a range or all of them.
Tensor Parallelism
Experimental: splits each tensor across N GPUs. Needs a fast link between GPUs (and NCCL at build time on CUDA), flash attention on and an f16 KV cache. N must divide the model's attention head count.
Custom
Your own --tensor-split string, passed through unchanged.

GPUs left out are hidden from the model with --device, so they stay free. Integrated GPUs are marked (iGPU) and never chosen for you; they need the Include iGPU Build Target build option.

Key settings

GPU Layers
Layers on the GPU; 999 means all.
Context Size
Larger needs more memory for the KV cache.
Flash Attention
Usually on: faster, less memory.
KV Cache Quant
q8_0 about halves KV memory at almost no quality cost; q4_0 saves more, with some loss.
Micro-batch (-ub) and Batch (-b)
Micro-batch usually has the biggest effect on prompt speed; measure it (Autotune or a benchmark sweep). Batch must be ≥ micro-batch. Defaults 512 and 2048.
Direct I/O
Loads weights without the OS page cache; useful when GPU memory is larger than system RAM.
Per-Layer Embeddings
Only for models with such a table (Gemma-3N, Gemma-4 E-series, Qwen4-Exp). Auto reads tables over 4 GiB from the file as needed. Has no effect with Direct I/O.
Vision Projector (mmproj)
Found automatically when it is in the model's folder.
Speculative Decoding
Predicts several tokens per step, with no change to the answer. A draft model gives the biggest gain; n-gram modes need no extra model. The ? button explains each mode.
Sampling
Applied per request, no restart. The Preset list offers defaults found in the GGUF, the Unsloth docs and the base model's generation_config.json. Blank fields still use the GGUF's own defaults. ↻ Refresh presets looks again.
Extra Flags
Any other llama-server flags, added as written.
Most changes need a server restart: press Restart required in the panel. Sampling changes do not.

Download Models

Search HuggingFace or ModelScope for GGUF repos and download single quants; downloads resume after an interruption. Gated models need a token for that host in Settings. The buttons above the search open Find recommended LLMs, Get embedding models and, with generation turned on, Get generation models.

Recommended models

Checks about 40 popular and new models against this machine and suggests the largest quant that fits at the chosen context size. Figures are estimates from the same planner Autoconfigure uses. A model downloaded from a card starts with that card's settings.

  • Sort: Best quality (larger models first; below about 4 bits per weight counts for less), Fastest (least data read per token, so mixture-of-experts models do well), Longest context, Newest.
  • Bits per weight: about 4.5 or more keeps nearly all quality; below 3 is never suggested.
  • Experts in system memory: a large mixture-of-experts model can run with some experts in RAM, more slowly. Dense models that would not fit on the GPU are left out.
  • The list is kept for six hours, or until the GPUs or build change; Refresh asks again.

Vision and audio models

Many vision models need a separate mmproj (projector) file from the same repo. Download it from the file list as well; once it is in the model's folder, Configure picks it up. Models with built-in vision show Vision: Built-in.

Audio models use a projector file too. Toolchest reads from it what the model can do and shows it as badges: vision reads images, audio understands speech (transcription, live voice with /v1/realtime), speech speaks (/tts). A model that only speaks, such as Qwen3-TTS, has no chat; it is left out of the agent configs. The audio routes need llama.cpp v0.8.0 or newer.

Parameters, sweeps and profiles

  • Each parameter defaults to the model's own setting. One value applies it to the whole job; several values make a sweep, one result per value. Parameters marked ↻ reload the model for each value; the preview shows how many reloads.
  • Saved profiles appear under each model as starting points; each checked profile is measured separately, exactly as saved (parameters are turned off). The job keeps a copy of each profile. ⚠ marks a profile saved on a build the job does not include.
  • Memory used: each result records the GPU memory its load used (needs Model loading detail 4). That shows the cost of a faster setting, such as a larger micro-batch.
  • Actions: Detail, Compare (pick rows, across jobs), Export (CSV or JSON) and Retry failed.
  • Results marked ⚠ unverified predate a fix to parameter overrides; re-run them if the settings matter.

Capability benchmarks

These score how good a model is rather than how fast. They load the model directly, so the server is stopped while one runs and started again afterwards. Image, video and music generation

Image and video generation (stable-diffusion.cpp's sd-server) and music (acestep.cpp's ace-server) can run next to llama-server. They are off until you turn them on.

  1. Turn on Generation backends in Settings.
  2. Build stable-diffusion.cpp and/or acestep.cpp on Builds (ROCm, CUDA, or Vulkan in host installs).
  3. Download a model set with Get generation models on Download Models. Files go in the models folder's gen-models folder. You can also add a custom set from files you have.
  4. Create an instance: on Models, under Generation models, press New instance and pick a build and GPU. It appears on Server.
  5. Measure it. One test generation records peak GPU memory; the reservation is that plus 10%. Sets that edit images also measure an edit. For video, choose a size (Short, Medium, Full or custom); the instance then refuses larger videos. A video test runs one sampling step (one on each expert for Wan2.2 A14B) and the whole decode: memory peaks there, and the other steps only take time. Once the instance has made a real video, its row shows how long that took. Once two sizes are measured, the Measure dialog shows, beside each other size, what it should need and whether that fits the card. The prediction draws a line through the two measurements (memory grows with frames × width × height); near the card's limit sd.cpp may decode in smaller pieces, which bends the line, so only Measure grants a size. Measure inside sets a smaller budget than the whole room, to leave space for other models: sd.cpp then holds model weights in system RAM and decodes in smaller pieces, so videos take longer, and the instance keeps to that budget afterwards. Measure stops as soon as the size needs more than the card can give, or when the test stops making progress (the GPU idle and the backend silent for 5 minutes, which a stuck tiled decode on a Radeon card does), and says how far it got. Start on an unmeasured instance offers to measure first.
  6. Start it, or turn on auto-start. Change it with Edit while stopped; changes other than auto-start clear the reservation.

  • Reservations are planned, not held. The LLM planner leaves them free (after a margin of 1 GiB or 8% of the card), and LLM loads that would crowd one out are refused: HTTP 507 from the API, an error from Load, benchmarks, Autotune and Autoconfigure. An enabled instance keeps its reservation while stopped.
  • llama-server's own chat page (port 8080) loads models without asking llama-toolchest, so it is not checked. On a GPU with reservations, load models from the Models page or the API.
  • sd-server is held to its reservation; ace-server's is a planning figure. sd-server keeps part of a set in system RAM on a smaller card, so measure on the card you will use.
  • Every catalog image and video set except SDXL runs its text encoder on the CPU (--backend te=cpu). On the R9700 this saved 4–5.5 GiB on each image set at no real cost, 6 GiB on TI2V 5B and 3 GiB on LTX-2.3 at Full (enough for Full to fit), for 13–16 s a video. Wan2.2 A14B saves only about 1 GiB, because sd.cpp already drops its encoder from GPU memory before sampling. An LLM running partly on the CPU and an image job slowed each other no more than before: the encoder runs only for a second or two. A custom set can do the same by adding --backend te=cpu to its launch arguments.
  • Which HunyuanVideo 1.5 set to pick: the I2V 480p step-distilled set for speed (about 2 minutes for a short video), a 480p CFG-distilled set for 50-step quality at half the base set's time, and a 720p set for detail when a short clip is enough.   • Example, one 32 GB R9700: Ming-Image fits beside Qwen-Image Turbo or ACE-Step XL, not both. With Qwen-Image Turbo and ACE-Step XL, about 8.6 GiB is left for an LLM.

Sharing a GPU

Jobs and chat on one GPU slow each other down (on one R9700: images 2.3× slower, songs 2.8×, chat 45 → 11–20 tokens/s). So generation jobs take turns: one per GPU, up to 16 waiting (more get HTTP 429). Chat never waits. Benchmarks, Autotune and Autoconfigure also wait for a running job and then keep the GPU until they finish. Jobs on separate GPUs run at full speed, as long as the LLM is not split onto those GPUs; set its GPU Assignment to keep it on its own card. Jobs started from a backend's own web page skip the queue.

Taking turns when both do not fit

By default an LLM that does not fit beside the reservations is refused. With Let LLMs and backends take a GPU from each other on (Settings → Generation backends):

  • Only running backends count. A chat request for an LLM that does not fit stops as few backends as needed on its GPUs, largest first, after any running job there finishes.
  • A job for a stopped backend starts it, stopping other backends and then unloading LLMs on that GPU (largest first) as needed. An LLM is unloaded only after its replies in progress finish; it loads again after the job.
  • The newest request wins, so chat and jobs on one GPU swap it each time, with a reload of seconds to a minute.
  • Lock an instance on the Server page to keep it from ever being stopped this way.
  • Keep the LLM's prompt cache saves conversations to disk before such an unload and restores them after (a 26,600-token conversation: 21 s to re-read, 1.1 s restored). Restart the router after turning it on.
  • Benchmarks, Autotune and Autoconfigure never stop backends; stop the backend first.

Image, video and music API

Instances appear in /v1/models with meta.kind image, video or music; use the instance or set ID as model. meta.api lists the routes each one supports, meta.video gives a video instance's limits, and meta.tasks a music instance's tasks. Every field and error is in the API reference.

KindWait for the resultJob (answers at once with an ID)Download
ImagePOST /v1/images/generations, /v1/images/editsPOST /v1/images/jobs…/jobs/{id}/image/0
VideoPOST /v1/videos/generationsPOST /v1/videos/jobs…/jobs/{id}/video
Music–POST /v1/music/jobs, or the ACE-Step routes /release_task, /query_result, /v1/audio…/jobs/{id}/audio
  • Jobs: GET a job until status is succeeded, failed or cancelled. phase shows progress (starting, queued, generating or composing/synthesizing, saving) and queue_position the jobs ahead. GET /v1/{images,videos,music}/jobs?status=… lists jobs.
  • DELETE cancels an unfinished job or deletes a finished one. A running image cannot be interrupted; a running video can. Results are kept 24 hours (videos: at most 50). Jobs survive a restart, but unfinished ones show failed.
  • Video: JSON or multipart with prompt, size, frames or seconds, fps, start_image, end_image, output_format (webm, with sound for LTX-2.3, or webp), extra. Requests above the measured size are refused (over_measured_size).
  • Music: caption, lyrics, duration. To work on an existing song, set task_type (cover, repaint, lego, extract, complete) and post it as multipart with an audio part. lego, extract and complete need a base model.

Each backend's own web page opens from Open web UI → on the Server page (port 8081 and up). In a container, those ports are published only if you chose that in setup.sh.

Using the API

The server speaks OpenAI's /v1/* API; point any OpenAI-compatible client at it. The API reference lists every route with a form to try it, and /openapi.json has the same for code generators.

curl $BASE/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "unsloth-Qwen3.5-4B.Q4_K_M",
    "messages": [{"role": "user", "content": "hello"}]
  }'

Troubleshooting

Start does nothing, or "no compiled build available"
There is no successful build. Build llama.cpp on Builds.
Model will not load, or llama-server crashes
Check Server Logs. If you use tensor parallelism, try a layer-split GPU Assignment.
Model missing from /v1/models
Check its On switch, then restart the server.
Stuck on "loading"
It probably failed to start; check Server Logs.
Out of GPU memory
Run Autoconfigure, or lower GPU Layers or Context Size, use KV Cache Quant, or lower Max Loaded.
No sampling presets
None were found for this model. Try ↻ Refresh presets later.
