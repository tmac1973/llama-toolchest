Llama Toolchest — Help

Run local LLMs with llama.cpp, plus image, video and music generation, from one web UI. This page gives short answers. The documentation has the full detail, with diagrams.

Quickstart

  1. Build llama.cpp. On Builds, pick the profile for your hardware (CUDA, ROCm, Vulkan, CPU) and start a build.
  2. Download a model. On Download Models, Find recommended LLMs lists models that fit this machine, or search for a GGUF repo and pick a quant (Q4_K_M is a good default).
  3. Enable it. On Models, turn on the model's On switch.
  4. Autoconfigure it. Press Autoconfigure on the model and say how long your conversations or documents are. Review the settings and press Save and apply. It calculates what fits in VRAM and test-loads it. For the advice of the publisher too, install the helper model on Settings first.
  5. Start the server. On Server, press Start.
  6. Autotune it (optional). Press Autotune on the model to measure faster speed settings. Then press Use these settings on the result you want. It takes a while, and the server cannot answer other requests while it runs.
  7. Send a request to the OpenAI-compatible address in the API Endpoint card, with the model's public name in the model field.

Core concepts

Enabled
The server offers the model in /v1/models and can load it on request. Uses no VRAM. Enable as many as you like.
Loaded
The model is in VRAM and ready. The router loads it on the first request, or when you press in the Server tab's Available Models card.
Max loaded models
How many models can be loaded at once (Settings → Eviction). 0 means no limit. See Eviction for what unloads when a new model needs room.
Public name and aliases
The id in /v1/models is a short name from the repo and quant (e.g. unsloth-Qwen3.5-4B.Q4_K_M). The long registry ID and any aliases you add in Configure → Aliases work too.

Eviction

Eviction is how toolchest makes room on a GPU for a new model. Off: the llama-server router keeps up to Max loaded models, of any size. llama.cpp: the router unloads idle models by VRAM; it cannot run with generation backends or forks. llama-toolchest: toolchest unloads idle LLMs on the GPUs that are short, and keeps the generation reservations free. Set it in Settings → Eviction; a new mode applies at the next server start.

More in the docs: a diagram of each mode, and the rules for small models.

Why generation models need reservations

A generation backend takes its memory only when a job starts, so toolchest keeps that room free for it. More in the docs

LLMs and backends taking turns

With LLMs and backends can take turns on a GPU on, the newest request gets the GPU: chat stops idle backends, and a job unloads idle LLMs. More in the docs

GPU memory margin

The margin is VRAM on each GPU that toolchest does not plan models or backends into. llama.cpp uses it for working memory in real chats, and the driver uses some too. The default and the smallest value is 1 GiB. Set one value for every GPU, or a larger one for a GPU that runs the desktop. If a load runs out of memory, raise the margin of that GPU by 0.5 to 1 GiB.

More in the docs: what toolchest counts on a GPU, and what the llama.cpp router gets.

Server tab

The Server tab starts and stops llama-server, picks its build, and shows the eviction mode in effect. It lists the models it serves, the API address with config files for coding agents, live speeds, and the server logs.

More in the docs

Engine notes

The line above the Server Logs counts loads, failed loads and crashes; Review keeps each crash with its error lines. More in the docs

Builds

Builds compile llama-server from a ggml-org/llama.cpp ref for one backend: CUDA, ROCm, Vulkan (host installs), Metal or CPU. Keep several builds, and choose one on the Server tab. Save toggles and extra CMake flags as a flag set to use them again on another ref.

More in the docs

llama.cpp + RDNA boosts

A set of patches that makes AMD RDNA2, RDNA3 and RDNA4 GPUs faster, on an older upstream base; choose llama.cpp + RDNA boosts and a ROCm profile. More in the docs

Models

Downloaded GGUFs, grouped by publisher and base model. Turn a model on with its On switch, open Configure for its settings, and check for a newer upload with Update. The Downloads card pauses, resumes and discards downloads.

More in the docs

Autoconfigure and Autotune

Autoconfigure suggests settings that fit in VRAM, from how long your conversations are, and test-loads them. Autotune then measures speed settings and keeps the fastest, as up to three profiles. Run Autoconfigure first: Autotune makes a model faster, not correct.

More in the docs

Model config (Configure)

The settings of one model: GPU Assignment, context size, KV cache type, batch sizes, speculative decoding, sampling, a default system prompt and extra flags. Most changes need a server restart; sampling and the system prompt do not.

More in the docs: what each setting does.

Download Models

Search HuggingFace or ModelScope for GGUF repos, and download one quant. Downloads resume after an interruption. Gated models need a token for that host in Settings.

More in the docs

Recommended models

Find recommended LLMs checks about 40 models against this machine and suggests the largest quant that fits. More in the docs

Benchmarks

A job runs every combination of the chosen models, builds and presets. Speed presets measure prompt reading (PP), generation (TG) and time to first token. Capability tests (perplexity, KL divergence, HellaSwag, Winogrande) score how good a model is; the server stops while one runs.

More in the docs: the presets, sweeps, and how to read each score.

Image, video and music generation

Image and video (sd-server) and music (ace-server) run next to llama-server. Turn on Generation backends in Settings, build the backend, get a model set, create an instance, and measure it.

More in the docs: model sets, custom sets, and each step.

Measured reservations

Measure records the peak VRAM of one test job; the reservation is that plus 10%, and the planner keeps it free. The docs list what each catalog set needed on two test cards. More in the docs · Measured reservations

Sharing a GPU

One job runs on each GPU, and up to 16 wait; more get HTTP 429. More in the docs

Taking turns when both do not fit

With take turns on, chat and jobs on one GPU swap it, with a reload each time; lock an instance to keep it running. More in the docs

Image, video and music API

Instances show in /v1/models with meta.kind. Send image, video and music requests to the OpenAI-style routes, or as jobs that answer at once with an ID. The API reference has every field. More in the docs

llama.cpp forks (experimental)

Build and run hand-picked forks of llama.cpp, each for the one model it is tuned for, next to the normal router. Turn them on in Settings.

More in the docs

Settings

Auto-start, the runtime environment of llama-server, eviction, the GPU memory margin, generation backends, backup and restore, the server URL, the API key, tokens for model hosts, and the models folder.

More in the docs

Using the API

The server speaks the OpenAI /v1/* API. Send requests to the address in the API Endpoint card, with the model's public name as model. The API reference lists every route with a form to try it.

More in the docs

Troubleshooting

  • Start does nothing: there is no successful build. Build llama.cpp on Builds.
  • A model will not load, or crashes: check the Server Logs, or Engine notes for an earlier crash.
  • Out of VRAM: run Autoconfigure, or raise the GPU memory margin of that GPU.
