Llama Toolchest — Help

Run local LLMs with llama.cpp, plus image, video and music generation, from one web UI.

Quickstart

  1. Build llama.cpp. On Builds, pick the profile for your hardware (CUDA, ROCm, Vulkan, CPU) and start a build.
  2. Download a model. On Download Models, Find recommended LLMs lists models that fit this machine, or search for a GGUF repo and pick a quant (Q4_K_M is a good default).
  3. Enable it. On Models, turn on the model's On switch.
  4. Autoconfigure it. Press Autoconfigure on the model and say how long your conversations or documents are. Review the settings and press Save and apply. It calculates what fits in VRAM and test-loads it. For the advice of the publisher too, install the helper model on Settings first.
  5. Start the server. On Server, press Start.
  6. Autotune it (optional). Press Autotune on the model to measure faster speed settings. Then press Use these settings on the result you want. It takes a while, and the server cannot answer other requests while it runs.
  7. Send a request to the OpenAI-compatible address in the API Endpoint card, with the model's public name in the model field.

Core concepts

Enabled
The server offers the model in /v1/models and can load it on request. Uses no VRAM. Enable as many as you like.
Loaded
The model is in VRAM and ready. The router loads it on the first request, or when you press in the Server tab's Available Models card.
Max Loaded
How many models can be loaded at once. When it is reached, the least recently used one is unloaded. 0 means no limit.
Let the router keep several models loaded
The llama-server router decides by VRAM, not by count. It keeps several models loaded, for example small embedding or speech models beside a large chat model. When a new model does not fit, the router unloads the least recently used idle models. It keeps a margin free on each GPU; the Server tab shows it. It never unloads a model that answers a request. A small model can unload a big one: if the big model leaves too little room on a GPU that the small model uses, a request for the small model unloads the big one. To keep both loaded, give the big model a smaller context. Needs llama.cpp b11930 or newer. Available only while generation backends are off, because the router cannot see their VRAM reservations. Benchmarks and Autotune still load one model at a time.
Public name and aliases
The id in /v1/models is a short name from the repo and quant (e.g. unsloth-Qwen3.5-4B.Q4_K_M). The long registry ID and any aliases you add in Configure → Aliases work too.

Engine notes
The line above the Server Logs counts what llama-server did in the last 24 hours. It turns amber when a model crashed or failed to load. Review shows more: router starts and stops, loads, failed loads, crashes and unloads, and a table for each model with its time loaded, average load time, requests and tokens. Choose the period at the top: 24 hours, 7 days, 30 days or all.
  • A crash is a model that stopped with an error and nobody asked it to stop. An unload, an eviction, or a stop that had to be forced is not a crash. A failed load is a model that stopped before it finished loading.
  • Each crash shows the time, the model, the exit status, the build, the GPUs, and the error lines from the log. What llama-server wrote shows the last lines of that model's output.
  • Events while a benchmark or Autotune job holds the router show the job's name. The requests of a job are not counted as model usage.
  • Requests count by the hour, for completions, chat, embeddings and rerank. A request that gets an error answer counts as a failed request.
  • The data is kept in engine-notes.json in the data folder, so it stays after a restart. It stays until you delete it: use Delete old data at the bottom of Review. The same data is at GET /api/service/notes?period=24h (or 7d, 30d, all) as JSON.
  • A crash also writes a WARN line to the toolchest log.

Builds

Builds compile llama-server from a ggml-org/llama.cpp ref for one backend. Several builds can be kept; choose one on the Server tab.

Profiles
Only backends found on this system show. CUDA: NVIDIA; needs the CUDA toolkit. ROCm: AMD; toolchest detects the GPU arch (set GPU_TARGETS in Extra CMake Flags to change it). With more than one ROCm, a ROCm Install picker shows. Vulkan: any vendor; host installs only. Metal: macOS. CPU: always available.
Ref
A release tag (b*) or latest. rocWMMA FlashAttention was removed at b10332, but it is still the fastest prompt reading on RDNA4. To use it, pin an older ref.
Options and Extra CMake Flags
Each toggle says when to use it. Extra CMake Flags takes anything else that CMake accepts; the preview shows the final flags. Vulkan tuning is in the runtime environment in Settings.
Saved flag sets
Enter a Build Tag and press Save Flags to keep toggles and extra flags under that name, then replay them on any ref.

Autoconfigure and Autotune

A profile is a named copy of a model's settings. The profile bar at the top of Configure saves and restores them. Profiles survive re-downloading the model and are included in backups.

AutoconfigureAutotune
DoesSuggests settings that fitMeasures many settings and keeps the fastest

AsksHow long your conversations or documents areWhat you use the model for (speculative decoding pays off most when answers repeat the prompt, as in code editing)
ResultA reviewed list of settings, each with a reason; Save as profile or Save and applyUp to three profiles: fastest generation, fastest prompt reading, fastest full answer
While it runsTest-loads the settings (restarts the server, unloads other models)Restarts the server for each setting; stop any time and continue later
  • Run Autoconfigure first. Autotune keeps the context, memory and sampling settings, so it makes a badly set-up model faster, not correct.
  • Test load. The memory estimate adds all GPUs together, but llama.cpp does not fill them evenly. If the test load runs out of memory, Autoconfigure tries these, in order: fewer layers on the full GPU, a smaller prompt batch, a smaller context. These settings show test load.
  • GPUs. On a machine with more than one GPU, select the GPUs that the model can use. Autoconfigure fits the model only on those GPUs. Clear a GPU to keep it for image, video or music models. Autotune then measures the model on the GPUs that the profile uses.
  • Helper model. Autoconfigure reads the model card with a small model of its own (install it on Settings). Without it, settings come only from what fits.
  • Noise. Autotune keeps the simpler setting unless the faster one wins by more than the run-to-run variation. Each stage is a normal benchmark job; you can read it on Benchmarks.

Model config (Configure)

GPU Assignment

GPU N / GPUs i-j / All GPUs
One GPU, or layers split across a range or all of them.
Tensor Parallelism
Experimental: splits each tensor over N GPUs. Needs a fast link between GPUs (and NCCL at build time on CUDA), flash attention on, and an f16 KV cache. N must divide the attention head count of the model.
Custom
Your own --tensor-split string, passed through unchanged.

GPUs that are left out are hidden from the model with --device, so they stay free. Integrated GPUs show (iGPU), and toolchest never chooses them for you. They need the Include iGPU Build Target build option.

Key settings

GPU Layers
Layers on the GPU; 999 means all.
Context Size
Larger needs more memory for the KV cache. For an embedding model, Context Size is the longest input of one request. Most embedding models read an input in one micro-batch, so toolchest raises the micro-batch to the same size. VRAM use grows fast: about 1 GiB at 8K and 7 GiB at 32K for EmbeddingGemma 2. The default is 8192, or the model's limit if it is lower.
Embedding models and GPUs
At download, toolchest puts an embedding model on the one GPU with the most room, if it fits. Spread over several GPUs, each GPU needs its own working memory for the model. That can be many times the model's size.
Parallel Conversations and Shared Context
With Shared Context on, all conversations use one context pool. A long conversation can use more than its part. If the pool fills, llama.cpp clears waiting conversations, and they read their prompt again. If that is not enough, a request fails. A per-conversation limit stops one conversation from taking the whole pool.
Flash Attention
Usually on: faster, less memory.
KV Cache Quant
q8_0 about halves KV memory at almost no quality cost; q4_0 saves more, with some loss.
Micro-batch (-ub) and Batch (-b)
Micro-batch usually has the largest effect on prompt speed; measure it with Autotune or a benchmark sweep. Batch must be ≥ micro-batch. Defaults: 512 and 2048.
Direct I/O
Loads weights without the OS page cache. Use it when VRAM is larger than system RAM.
Per-Layer Embeddings
Only for models with such a table (Gemma-3N, Gemma-4 E-series, Qwen4-Exp). Auto reads tables over 4 GiB from the file as needed. Has no effect with Direct I/O.
Projector (mmproj)
Lets the model read images or audio, or speak. Toolchest finds it when it is in the model's folder.
Speculative Decoding
Predicts several tokens per step, with no change to the answer. A draft model gives the biggest gain; n-gram modes need no extra model. The ? button explains each mode.
N-gram Cache file
With llama.cpp b11758 or newer, toolchest keeps what N-gram Cache learns in /data/cache/ngram/<model id>.bin. llama-server reads the file at load and writes it at unload. Benchmarks and Autotune do not use it. A broken file makes llama-server stop at load, so toolchest deletes a broken file before a load. Clear learned n-grams deletes the file; a loaded model writes it again at unload.
Sampling
Applies per request, with no restart. The Preset list shows defaults from the GGUF, the Unsloth docs and the generation_config.json of the base model. Empty fields still use the GGUF defaults. ↻ Refresh presets looks again.
Extra Flags
Any other llama-server flags, added as written.
Most changes need a server restart: press Restart required in the panel. Sampling changes do not.

Download Models

Search HuggingFace or ModelScope for GGUF repos and download single quants. Downloads resume after an interruption. Gated models need a token for that host in Settings. The buttons above the search open Find recommended LLMs, Get embedding models and, with generation on, Get generation models.

Recommended models

Checks about 40 popular and new models against this machine. It suggests the largest quant that fits at the chosen context size. The figures are estimates from the same planner as Autoconfigure. A model downloaded from a card starts with the settings of that card.

  • Sort: Best quality (larger models first; below about 4 bits per weight counts for less), Fastest (least data read per token, so mixture-of-experts models do well), Longest context, Newest.
  • Bits per weight: about 4.5 or more keeps nearly all quality; below 3 is never suggested.
  • Experts in system memory: a large MoE model can run with some experts in RAM, more slowly. Dense models that do not fit on the GPU are left out.
  • The list stays for six hours, or until the GPUs or build change. Refresh asks again.

Vision and audio models

Many vision models need a separate mmproj (projector) file from the same repo. Download it from the file list too. When it is in the model folder, Configure finds it. Models with built-in vision show Vision: Built-in.

Audio models use a projector file too. Toolchest reads from it what the model can do and shows badges: vision reads images, audio understands speech (transcription, live voice with /v1/realtime), speech speaks (/tts). A model that only speaks, such as Qwen3-TTS, cannot chat, so the agent configs leave it out. The audio routes need llama.cpp v0.8.0 or newer.

Parameters, sweeps and profiles

  • Each parameter uses the setting of the model by default. One value applies to the whole job. Several values make a sweep, with one result per value. Parameters marked ↻ reload the model for each value; the preview shows the number of reloads.
  • Saved profiles show under each model as start points. Each checked profile is measured on its own, exactly as saved, so the parameters turn off. The job keeps a copy of each profile. ⚠ marks a profile saved on a build that the job does not include.
  • Memory used: each result records the VRAM that its load used (needs Model loading detail 4). It shows the cost of a faster setting, such as a larger micro-batch.
  • Actions: Detail, Compare (pick rows, across jobs), Export (CSV or JSON) and Retry failed.
  • Results marked ⚠ unverified are older than a fix to parameter overrides. Run them again if the settings matter.

Image, video and music generation

Image and video generation (sd-server of stable-diffusion.cpp) and music (ace-server of acestep.cpp) can run next to llama-server. They are off until you turn them on.

  1. Turn on Generation backends in Settings.
  2. Build stable-diffusion.cpp and/or acestep.cpp on Builds (ROCm, CUDA, or Vulkan in host installs).
  3. Download a model set with Get generation models on Download Models. Files go in the gen-models folder of the models folder. You can also add a custom set from your own files.
  4. Create an instance: on Models, under Generation models, press New instance and choose a build and GPU. It shows on Server.
  5. Measure it. One test generation records the peak VRAM; the reservation is that plus 10%. Start on an unmeasured instance offers to measure first.
    • Sets that edit images also measure an edit.
    • Video: choose a size (Short, Medium, Full or custom). The instance then refuses larger videos.
    • A video test runs one sampling step (one per expert for Wan2.2 A14B) and the whole decode. The peak is in the decode; the other steps only add time. After the instance makes a real video, its row shows how long it took.
    • After two sizes are measured, the Measure dialog shows for each other size what it should need and if it fits the card. The prediction is a line through the two measurements: memory grows with frames × width × height. Near the card limit, sd.cpp can decode in parts, which bends the line. So only Measure grants a size.
    • Measure inside sets a budget smaller than the whole room, to leave space for other models. sd.cpp then keeps weights in system RAM and decodes in parts, so videos are slower. The instance keeps that budget after.
    • Measure stops when the size needs more than the card has, or when the test stops making progress: the GPU idle and the backend silent for 5 minutes, as a stuck tiled decode on a Radeon card does. It says how far it got.
  6. Start it, or turn on auto-start. Change it with Edit while it is stopped. Changes other than auto-start clear the reservation.

  • Reservations are planned, not held. The LLM planner keeps them free, after a margin of 1 GiB or 8% of the card. It refuses an LLM load that would crowd one out: HTTP 507 from the API, an error from Load, benchmarks, Autotune and Autoconfigure. An enabled instance keeps its reservation while it is stopped.
  • The chat page of llama-server (port 8080) loads models without toolchest, so toolchest cannot check them. On a GPU with reservations, load models from the Models page or the API.
  • sd-server stays within its reservation; the ace-server figure is for planning only. On a smaller card, sd-server keeps part of a set in system RAM, so measure on the card you will use.
  • All catalog image and video sets except SDXL run their text encoder on the CPU (--backend te=cpu). On the R9700 this saved 4–5.5 GiB per image set at no real cost. It saved 6 GiB on TI2V 5B and 3 GiB on LTX-2.3 at Full, enough to make Full fit; each video takes 13–16 s longer. Wan2.2 A14B saves only about 1 GiB, because sd.cpp already removes its encoder from VRAM before sampling. An LLM partly on the CPU and an image job do not slow each other more than before: the encoder runs for only a second or two. A custom set can do the same with --backend te=cpu in its launch arguments.
  • Which HunyuanVideo 1.5 set: the I2V 480p step-distilled set for speed (about 2 minutes for a short video); a 480p CFG-distilled set for 50-step quality in half the time of the base set; a 720p set for detail when a short clip is enough. I2V sets need a start image; T2V sets need only text. Their licence, the Tencent Hunyuan Community License, is not valid in the EU, the UK or South Korea.   • An instance measured before its set settings changed shows Measured with older settings. Measure it again: it can need less memory now.
  • Example, one 32 GB R9700: Ming-Image fits beside Qwen-Image Turbo or ACE-Step XL, not both. With Qwen-Image Turbo and ACE-Step XL, about 8.6 GiB is left for an LLM.

Sharing a GPU

Jobs and chat on one GPU slow each other (on one R9700: images 2.3× slower, songs 2.8× slower, chat from 45 to 11–20 tokens/s). So generation jobs take turns: one per GPU, up to 16 waiting; more get HTTP 429. Chat never waits. Benchmarks, Autotune and Autoconfigure also wait for a running job, then keep the GPU until they finish. Jobs on separate GPUs run at full speed if the LLM is not split onto those GPUs: set its GPU Assignment to keep it on its own card, or clear the generation GPU in Autoconfigure. Jobs from the own web page of a backend skip the queue.

Taking turns when both do not fit

By default, toolchest refuses an LLM that does not fit beside the reservations. With Let LLMs and backends take a GPU from each other on (Settings → Generation backends):

  • Only running backends count. A chat request for an LLM that does not fit stops as few backends as needed on its GPUs, largest first. It waits for a running job there to finish.
  • A job for a stopped backend starts it. It stops other backends first, then unloads LLMs on that GPU, largest first, as needed. An LLM unloads only after its replies in progress finish, and it loads again after the job.
  • The newest request wins, so chat and jobs on one GPU swap it each time, with a reload of seconds to a minute.
  • Lock an instance on the Server page, so that it never stops this way.
  • Keep the LLM's prompt cache saves conversations to disk before such an unload and restores them after (a 26,600-token conversation: 21 s to read again, 1.1 s to restore). Restart the router after you turn it on.
  • Benchmarks, Autotune and Autoconfigure never stop backends. Stop the backend first.

Image, video and music API

Instances show in /v1/models with meta.kind image, video or music. Use the instance or set ID as model. meta.api lists the routes of each instance, meta.video the limits of a video instance, and meta.tasks the tasks of a music instance. The API reference has every field and error.

KindWait for the resultJob (answers at once with an ID)Download
ImagePOST /v1/images/generations, /v1/images/editsPOST /v1/images/jobs…/jobs/{id}/image/0
VideoPOST /v1/videos/generationsPOST /v1/videos/jobs…/jobs/{id}/video
Music–POST /v1/music/jobs, or the ACE-Step routes /release_task, /query_result, /v1/audio…/jobs/{id}/audio
  • Jobs: GET a job until status is succeeded, failed or cancelled. phase shows progress (starting, queued, generating or composing/synthesizing, saving) and queue_position the jobs ahead. GET /v1/{images,videos,music}/jobs?status=… lists jobs.
  • DELETE cancels an unfinished job or deletes a finished one. A running image cannot stop; a running video can. Results stay 24 hours (videos: at most 50). Jobs survive a restart, but unfinished ones show failed.
  • Image: a job takes the JSON of /v1/images/generations, or the multipart form of /v1/images/edits for an edit. Edits need a set with the edit capability.
  • Video: JSON or multipart with prompt, size, frames or seconds, fps, start_image, end_image, output_format (webm, with sound for LTX-2.3, or webp), extra. Requests above the measured size are refused (over_measured_size).
  • Music: caption, lyrics, duration. To work on an existing song, set task_type (cover, repaint, lego, extract, complete) and post it as multipart with an audio part. lego, extract and complete need a base model.

{"model": "ming-image", "size": "1024x1024", "response_format": "b64_json",
 "prompt": "<sd_cpp_extra_args>{\"init_image\": \"iVBORw0KGgo…\", \"strength\": 0.9}</sd_cpp_extra_args>RGBA, 4-channel, transparent background. a red fox sticker"}

Open web UI → on the Server page opens the own web page of each backend (port 8081 and up). In a container, toolchest publishes those ports only if you chose that in setup.sh.

Settings

Auto-start
Start llama-server when llama-toolchest starts.
Runtime environment
Environment variables for llama-server and every model, applied at the next restart. The list is short on purpose; most tuning tips have no effect. Extra environment takes anything else (KEY=VALUE per line, applied last). Effective environment shows the result, with values set outside toolchest (systemd, container), which win.
Backup & Restore
One JSON file with settings, environment, flag sets and per-model configs. Configs match by repo and quant, so they restore on another machine. Secrets only if you tick the box. Restore merges and never deletes. Configs for models you do not have wait as pending until the download. Benchmark history is not included. Scripts: GET /api/backup, POST /api/restore.
Server URL
The address for the API and chat links. Change it if you open the UI from another machine.
API Key
Optional Bearer token for /v1/*.
HF Token
For gated models.
Models directory
Where GGUFs and downloads go (default <data dir>/models). Restart after you change it.
Theme
Saved in this browser.

Using the API

The server speaks the OpenAI /v1/* API. Point any OpenAI-compatible client at it. The API reference lists every route with a form to try it, and /openapi.json has the same for code generators.

curl $BASE/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "unsloth-Qwen3.5-4B.Q4_K_M",
    "messages": [{"role": "user", "content": "hello"}]
  }'

Troubleshooting

Start does nothing, or "no compiled build available"
There is no successful build. Build llama.cpp on Builds.
Model will not load, or llama-server crashes
Check Server Logs. The Server Logs start again with each router start, so for an earlier crash use Engine notes: it keeps each crash with its error lines. If you use tensor parallelism, try a layer-split GPU Assignment.
Model missing from /v1/models
Check its On switch, then restart the server.
Stuck on "loading"
It probably failed to start; check Server Logs.
Out of VRAM
Run Autoconfigure, or lower GPU Layers or Context Size, use KV Cache Quant, or lower Max Loaded.
No sampling presets
None were found for this model. Try ↻ Refresh presets later.
