Speculative Decoding — predict multiple tokens per step for faster generation. Restart required.
Speculative Decoding

Speculative decoding predicts multiple tokens ahead, then verifies them in one batch. Correct predictions are accepted for free. Output quality is never affected — the result is identical to normal generation.

Modes
Draft Model
Uses a separate smaller model of the same architecture to propose tokens. Highest and most consistent speedups (1.5-2.5x typical). Requires a compatible model — download one with the same architecture but smaller size (e.g., 0.5B-1B) and it will appear in the dropdown. Uses extra VRAM for the draft model.
MTP (Multi-Token Prediction)
Multi-token prediction comes in two flavors, both selected here. Self-speculation (Qwen3.6-MTP, DeepSeek-V3-MTP): the same GGUF carries an MTP head that drafts tokens for itself — no separate file needed. Separate drafter (gemma-4): ships an "assistant" head as its own GGUF (in an MTP/ subfolder); llama-toolchest auto-detects it and loads it via --model-draft. Typical speedup 1.5-3x with little or no extra VRAM. Notes: typically needs parallel = 1; gemma-4's gemma4-assistant arch requires a llama.cpp build of b9549 or newer (Gemma-4 MTP merged 2026-06-07) — build the latest from the Builds tab if an older one is in use.
N-gram Simple
Searches the generation history for matching token patterns and reuses what followed. Zero overhead, no extra VRAM. Works best when the model repeats patterns (code refactoring, structured output). No benefit for entirely novel text.
N-gram Cache
Keeps statistics about which tokens follow which short runs of tokens and uses them for drafting. With llama.cpp b11758 or newer, toolchest keeps what it learned in a file for each model, so it improves across loads instead of starting empty each time; benchmarks and Autotune start empty.
N-gram Map-K
Tracks n-gram patterns with a confidence threshold — only drafts when a pattern has been seen multiple times. More conservative than Simple (fewer drafts, but higher acceptance rate). Good when you want selective, high-confidence speculation.
N-gram Map-K4V
Experimental variant that tracks up to 4 different continuations per pattern and picks the most frequent one. Useful for patterns that lead to a few different outputs.
N-gram Mod (recommended n-gram assist)
Uses a lightweight shared hash pool (~16 MB) to learn patterns across requests. Patterns from one conversation benefit the next. Best general-purpose n-gram method — especially good for reasoning models, code, and multi-turn chat. Cold start is slow but improves over time.
EAGLE-3, DFlash, DSpark
Each loads a small trained head built for one specific model, published alongside it. A head is not a smaller model of the same family, so the drafter list for these modes is not filtered by architecture or size — pick the converted head for this model. They claim higher acceptance than a same-size draft model at a fraction of the memory. The settings are left blank because there is no measured guidance for them here; run a benchmark sweep to find good values rather than trusting a guess.
Running both at once

A draft method and an n-gram assist can run together, and they cost each other nothing on new text. On text the model is repeating — a file it is rewriting, a structured response, a tool-call loop — the n-gram assist is several times faster than a draft method alone. Neither one gives you both: an n-gram method is no help at all on genuinely new text, and a draft method gives up most of the speed on repeated text.

When both propose tokens for the same step, the n-gram proposal is the one used. That is worth knowing when you read a benchmark result: if a combined run comes out slower than the draft method alone on new text, it is because weak n-gram matches are displacing good draft proposals. Whether that happens depends on the model and the hardware, so measure it — the benchmark sweep can run the same model with the draft method alone and with both, side by side.

Parameters

Each slot has its own settings, because the two do not share a draft length: MTP might draft 3 tokens while N-gram Mod drafts 64, and both are in effect at once.

Draft tokens max / min (draft method)
How many tokens the draft method proposes per step, and how many it always proposes before verifying. Higher maximums mean more aggressive speculation; 32-64 suits MoE models, less for dense ones if acceptance is low. Leave blank to use llama.cpp's own defaults of 3 and 0.
Draft probability min (draft method)
Stops drafting once a token's probability falls below this. Lower drafts more tokens at a lower acceptance rate; higher drafts fewer, more accurate ones. Mainly useful for Draft Model — MTP and the trained heads have their own acceptance logic.
Assist tokens max / min (N-gram Mod)
How long a continuation N-gram Mod proposes. Much larger than a draft model's, because a matched pattern can be replayed at length: 64 and 48 are the recommended starting values.
Match length (N-gram Mod, default: 24)
How many recent tokens must match before a continuation is proposed. Longer means fewer but more reliable matches.
Lookup size (other n-gram methods, default: 12)
How many recent tokens are used as the search key. Larger means fewer but more precise matches.
Draft size (other n-gram methods, default: 48)
How many tokens following a match are proposed. Larger values pay off more when patterns repeat at length.
Minimum hits (other n-gram methods, default: 1)
How many times a pattern must have been seen before it is proposed. Higher is more selective: fewer drafts, higher acceptance.
When to use it
  • Large models where generation is the bottleneck
  • Repetitive workloads: code, structured output, reasoning traces
  • Multi-turn chat (N-gram Mod learns across requests)
When to skip it
  • Small/fast models — overhead exceeds gains
  • VRAM-constrained and no draft model — try N-gram Mod on its own, with the draft method left Disabled
  • Very short completions (few tokens) — not enough to amortize
  • Acceptance rate consistently below ~50% — will slow things down
